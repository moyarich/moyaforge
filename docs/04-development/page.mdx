# Development

This section describes **maintainer workflows**, not public package release capabilities.

## Requirements

Use Node.js 24 and npm from the repository root.

```sh
npm ci
npm run dev
```

`npm run dev` launches the private `apps/playground` workspace, building local workspace packages first.

## Test the CLI from another repository (without publishing)

The CLI is the `@moyarich/moyaforge-cli` workspace at
`packages/moyaforge-cli/`. Its executable is named `moyaforge` (declared
in that workspace's `package.json`), and the build outputs
`dist/bin/moyaforge.js`. These workflows use **local source** instead of
`@latest` from npm. Use Node.js 24.11+.

For the examples below, assume two sibling checkouts:

```text
projects/
├── moyaforge/               # This repository (npm workspaces)
│   └── packages/moyaforge-cli/
└── my-app/                  # Separate consuming repository
```

### Option 1: Run the workspace CLI using its local path

Build the CLI before invoking it in the consuming repository:

```sh
cd projects/moyaforge
npm ci
npm run build --workspace @moyarich/moyaforge-cli

cd ../my-app
npm exec --yes --package=../moyaforge/packages/moyaforge-cli -- moyaforge init --template playground --search
npm run dev
```

The `--` separates npm's arguments from the `moyaforge` CLI arguments.
The final `npm run dev` runs **in the consumer project**, after the
scaffold command has created its scripts. If the CLI generates into a new
subdirectory, change into that directory first. Rebuild after editing the
CLI's TypeScript source.

### Option 2: Link the CLI for repeated local development

Run `npm link` in the built CLI workspace to register its `moyaforge`
binary, then invoke that binary from any other repository:

```sh
cd projects/moyaforge
npm ci
npm run build --workspace @moyarich/moyaforge-cli

cd packages/moyaforge-cli
npm link

cd ../../../my-app
moyaforge init --template playground --search
npm run dev
```

The linked executable uses your local checkout. Rebuild the CLI after
source changes; `npm link` does not compile TypeScript or watch files.
When finished, run `npm unlink -g @moyarich/moyaforge-cli` to remove
the global link.

### Option 3: Install a packed CLI from the checkout

To test the same package contents that would be published, produce a
tarball and install or run it in the consumer repository:

```sh
cd projects/moyaforge
npm ci
npm run build --workspace @moyarich/moyaforge-cli
npm pack --workspace @moyarich/moyaforge-cli --pack-destination /tmp

cd ../my-app
npm exec --yes --package=/tmp/moyarich-moyaforge-cli-0.1.0.tgz -- moyaforge init --template playground --search
npm run dev
```

Replace the tarball path with the filename printed by `npm pack`
(the version changes with releases). The tarball approach also works
when copying the package to a different machine without publishing it.

### Running directly from GitHub

For a **standalone CLI repository** with its `package.json` at the
repository root and a built executable (or a working install-time build
script), npm can install the GitHub repository and execute its binary:

```sh
npm exec --yes --package=github:OWNER/CLI_REPO -- moyaforge init --template playground --search
```

**MoyaForge supports GitHub-root execution.** The root package exposes
`moyaforge` as a binary and its npm `prepare` hook builds the CLI workspace,
then copies the built `dist/` and scaffolding `templates/` into a
self-contained `github-cli/` folder for npm's Git package installation.
No npm publication or local clone is required:

```sh
npm exec --yes --package=github:moyarich/moyaforge -- moyaforge init --template playground --search
npm run dev
```

Run these commands from the **consumer** repository. The GitHub dependency
uses the default branch unless you append a Git ref, for example
`github:moyarich/moyaforge#main` or a commit SHA. It installs a temporary
CLI package rather than switching to the source workspace. Git installs
run the root preparation script, so they must have npm, Node.js 24.11+,
and access to install build dependencies. Preparation takes longer than
running the already-published CLI. The consuming app still installs its
generated application dependencies separately.

### Choose a method

| Method | Best for |
| --- | --- |
| Local path with `npm exec --package` | One-off testing from a sibling repository |
| `npm link` | Frequent edits and CLI runs against local source |
| `npm pack` | Verifying publishable package contents without publishing |
| GitHub package URL | Run this monorepo's CLI directly from GitHub without npm publishing |

### Maintaining the GitHub-root distribution

The root `package.json` owns the `moyaforge` binary mapping, a
`prepare` script, and the `github-cli/` packaging whitelist.
`scripts/prepare-github-cli.ts` copies the built CLI workspace output and
template assets into `github-cli/`. This directory is generated and should
not be committed. Keep both the executable and templates present when
changing the CLI's compiled layout.

To check the package before pushing changes, use:

```sh
npm run prepare
npm pack --dry-run --json
```

Confirm the file list includes `github-cli/dist/bin/moyaforge.js` and
`github-cli/templates/`. For an end-to-end check, run the GitHub-root
command above from a clean test consumer directory against a pushed commit.
A dry-run pack verifies file inclusion, but does not test Git installation
or scaffolding by itself.

The published command remains
`npx @moyarich/moyaforge-cli@latest init --template playground --search`.
Use it when you explicitly want to test the **published npm version**;
it does not test unmerged or unpublished changes in your checkout.

## Script conventions

Automation and maintenance scripts in `scripts/` and
`apps/playground/scripts/` use TypeScript (`.ts`), executed by Node.js
24.11+ directly when appropriate. Do not add new `.mjs`, `.cjs`, or
`.js` scripts to these directories. `npm run check:script-extensions`
enforces this convention.

The repository's root `npm run build` already delegates to
`npm run build --workspaces --if-present`. Use that command for
workspace compilation instead of introducing redundant build wrapper
scripts. The remaining dedicated scripts perform **non-build tasks**
such as package-content auditing, tarball verification, generated
registry reporting, and GitHub CLI bundling. They are not replaced by
workspace builds.

## Test and build

Unit and regression tests use **Vitest** across the workspaces. Run the workspace test scripts through npm rather than replacing the repository's test command:

```sh
npm run typecheck
npm test --workspaces
npm run check:links
npm run build
npm run test:consumer:browser
npm run test:e2e
```

Playwright browser tests require Chromium to be installed, for example `npx playwright install chromium`.

## Authoring documentation links

The playground reads the authored-content registry from `apps/playground/registry.config.ts`. This is separate from the installable component registry described above. The MDX link transform runs at **build time**, using the registry's source directories and discovered public routes; the browser router determines the final URL format.

### Source-file links (recommended for repository browsing)

Write a relative Markdown link to the real `.md` or `.mdx` file. For example, from `packages/moyaforge-ui/docs/page.mdx`:

```mdx
[Code Block](./01-components/10-code-block/page.mdx)
[Code Block usage](./01-components/10-code-block/page.mdx#usage)
```

GitHub can follow these file paths directly. In the built playground, the opt-in `remarkSourceLinks` transform looks up the target file in the discovered registry and rewrites it to the public route, such as `/ui/components/code-block`. The site's `HashRouter` then renders that as a GitHub Pages URL containing `#/ui/components/code-block`; a `BrowserRouter` host uses normal paths instead.

```js
import {
  discoverContent,
  remarkSourceLinks,
  createMdxOptions,
} from "@moyarich/moyaforge-mdx";

const { registry: discovered } = await discoverContent(registry, root);
const mdxOptions = createMdxOptions({
  remarkPlugins: [
    [
      remarkSourceLinks,
      {
        config: registry,
        root,
        routes: discovered.routes,
      },
    ],
  ],
});
```

The transform needs the original MDX file path supplied by the compiler. It resolves relative filenames against that file's directory, **not** against the page URL. Paths must correspond to an enabled registered page to be rewritten; the compiler does not invent routes for arbitrary repository files.

### Public-route links

If the author intends an application-specific documentation URL, link to its registry route:

```mdx
[Code Block](/ui/components/code-block)
[UI overview](/ui)
```

These are already public paths, so they do not undergo filesystem-source resolution. The playground MDX renderer uses the discovered routes for in-app navigation. Because GitHub itself does not serve those paths as repository files, prefer source-file links when the Markdown must be navigable in GitHub's source viewer.

### External links, assets, and fragments

```mdx
[MoyaForge repository](https://github.com/moyarich/moyaforge)
[Contact](mailto:example@example.com)
[Jump to this section](#authoring-documentation-links)
```

External schemes are not rewritten. Bare heading fragments keep the current page and are handled by the host's router. Asset links and unregistered file destinations are not converted into documentation pages.

### Source links versus GitHub edit links

A link **inside the MDX document** can target either a source file or a public route. The **Contribute on GitHub** control is different: it derives the repository-relative `sourcePath` from registry discovery and constructs the GitHub edit URL. The playground must not hardcode per-source directory mappings.

### Validation

Run `npm run check:links` and `npm test --workspaces` (Vitest) after changing documentation structure. A successful build alone does not guarantee that an unregistered source-file link, invalid heading fragment, or external destination is valid. Missing-target diagnostics and coverage for cross-source source links are tracked in [issue #193](https://github.com/moyarich/moyaforge/issues/193).

## Component registry generation

The source of truth for installable components is `packages/moyaforge-ui/src/components/` and compositions in `registry/templates/`. The generated `registry.json` is **not** the playground's authored-content `registry.config.ts`. Components own their CSS imports; styles stay beside their component source.

To check generated registry output locally, run:

```sh
npm run registry:build
npm run registry:check
npx --yes shadcn@4.21.5 registry validate ./registry.json
```

Registry generation and freshness enforcement run on `main`, not feature branches. PR CI runs workspace tests and other checks without rejecting changes merely because the generated registry is stale.

### Manual GitHub Actions verification

In **Actions → Build component registry → Run workflow**, select `main` and start the run. This invokes `workflow_dispatch` on the selected ref. For an unchanged branch, verify that regeneration, freshness checks, and shadcn validation pass and the final step reports **Registry is already current.** with no new commit.

To exercise changed output, merge a canonical component-source change into `main`; the workflow rebuilds the registry and commits only `registry.json` when needed. A validation failure must stop before the commit step.

The workflow runs only on `main`, including manual dispatch on `main`. It uses `GITHUB_TOKEN` with `contents: write`, checks out the current `main` tip, and serializes runs by Git ref without canceling an in-progress run. The final push is an ordinary non-force push; if another commit moves the branch, its push must be rejected rather than overwriting the new head. Repository branch-protection/ruleset settings must permit the intended bot update, or the workflow will fail visibly. Do not grant bypass permissions or configure a personal token just to make the job succeed. This workflow does **not** publish npm packages.

## MDX package source ownership

The implementation of `@moyarich/moyaforge-mdx` is grouped by responsibility instead of keeping all source modules at the root:

| Directory             | Responsibility                                                               |
| --------------------- | ---------------------------------------------------------------------------- |
| `src/content/`        | Content discovery, headings, source-file rules, link analysis and validation |
| `src/navigation/`     | Navigation trees, documentation groups and table-of-contents selection       |
| `src/registry/`       | Normalized page registry and route metadata                                  |
| `src/plugins/remark/` | Remark plugins and custom directive mapping                                  |
| `src/vite/`           | Vite adapter and virtual module generation                                   |

The `src/index.ts` package entry point aggregates the public compiler and registry API. Other supported package subpaths (`/navigation`, `/toc`, `/source-files`, `/vite`) point directly to their implementation files through `package.json` exports. **Do not add source-level compatibility re-export files** solely to retain old directory paths. When relocating source code, update internal imports, the public export map, compiled-module test imports, and CI tarball assertions together.

Release-note labels are applied by the reusable classifier on `pull_request_target` using `GITHUB_TOKEN`. If the classifier reports `Resource not accessible by integration (HTTP 403)` despite its declared `issues: write` permission, inspect repository or organization Actions token restrictions; changing the runtime compiler or test workflow will not resolve a denied API write. Classification remains advisory and must not block tests.

## Ownership and release notes

- `docs/` owns the general documentation and development guide; component examples live alongside their UI component documentation under `packages/moyaforge-ui/docs/`. `apps/playground` only renders these sources.
- `packages/*/CHANGELOG.md` and package release drafts describe **user-visible capabilities and fixes** of the respective publishable packages.
- CI mechanics, lockfile regeneration, release automation, contributor setup, private playground maintenance, and development-only tests belong here or in contributor documentation, **not in public changelogs**.
- Update a public changelog only when a released package's behavior or public API changes.
- The release-note classification workflow automatically applies `skip-changelog` to maintenance-style PR titles (`chore:`, `ci:`, `docs:`, `test:`, `build:`, `refactor:` and `style:`) or PRs without public package implementation changes. Feature and fix PRs touching published source remain eligible. Reviewers may also apply `skip-changelog` explicitly.
