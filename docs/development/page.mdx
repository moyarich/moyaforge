# Development

This section describes **maintainer workflows**, not public package release capabilities.

## Requirements

Use Node.js 24 and npm from the repository root.

```sh
npm ci
npm run dev
```

`npm run dev` launches the private `apps/playground` workspace, building local workspace packages first.

## Test and build

```sh
npm run typecheck
npm test
npm run test:unit
npm run check:links
npm run build
npm run test:consumer:browser
npm run test:e2e
```

Playwright browser tests require Chromium to be installed, for example `npx playwright install chromium`.

## Component registry generation

The source of truth for installable components is `packages/moyaforge/src/components/` and compositions in `registry/templates/`. The generated `registry.json` and `registry/styles/*.css` are **not** the playground's authored-content `registry.config.ts`.

After changing components, imports, package dependencies, or templates, regenerate and verify before opening a PR:

```sh
npm run registry:build
npm run registry:check
npx --yes shadcn@4.21.5 registry validate ./registry.json
```

Include the generated manifest and styles in the PR. Normal PR CI rejects stale output.

### Manual GitHub Actions verification

In **Actions → Build component registry → Run workflow**, select the branch to test and start the run. This invokes `workflow_dispatch` on the selected ref. For an unchanged branch, verify that regeneration, freshness checks, and shadcn validation pass and the final step reports **Registry is already current.** with no new commit.

To exercise changed output, push a temporary test branch with a canonical component-source change but without regenerated files, then dispatch the workflow on that branch. Verify that it creates a `github-actions[bot]` commit containing **only** `registry.json` and `registry/styles/**`. Inspect the commit before merging or deleting the branch. A validation failure must stop before the commit step.

The workflow uses the repository `GITHUB_TOKEN` with `contents: write`, checks out the selected branch tip, and serializes runs by Git ref without canceling an in-progress run. The final push is an ordinary non-force push; if another commit moves the branch, its push must be rejected rather than overwriting the new head. Repository branch-protection/ruleset settings must permit the intended bot update, or the workflow will fail visibly. Do not grant bypass permissions or configure a personal token just to make the job succeed. This workflow does **not** publish npm packages.

## MDX package source ownership

The implementation of `@moyarich/moyaforge-mdx` is grouped by responsibility instead of keeping all source modules at the root:

| Directory | Responsibility |
| --- | --- |
| `src/content/` | Content discovery, headings, source-file rules, link analysis and validation |
| `src/navigation/` | Navigation trees, documentation groups and table-of-contents selection |
| `src/registry/` | Normalized page registry and route metadata |
| `src/plugins/remark/` | Remark plugins and custom directive mapping |
| `src/vite/` | Vite adapter and virtual module generation |

The `src/index.ts` package entry point aggregates the public compiler and registry API. Other supported package subpaths (`/navigation`, `/toc`, `/source-files`, `/vite`) point directly to their implementation files through `package.json` exports. **Do not add source-level compatibility re-export files** solely to retain old directory paths. When relocating source code, update internal imports, the public export map, compiled-module test imports, and CI tarball assertions together.

Release-note labels are applied by the reusable classifier on `pull_request_target` using `GITHUB_TOKEN`. If the classifier reports `Resource not accessible by integration (HTTP 403)` despite its declared `issues: write` permission, inspect repository or organization Actions token restrictions; changing the runtime compiler or test workflow will not resolve a denied API write. Classification remains advisory and must not block tests.

## Ownership and release notes

- `docs/` owns the documentation, examples, and development guide; `apps/playground` only renders them.
- `packages/*/CHANGELOG.md` and package release drafts describe **user-visible capabilities and fixes** of the respective publishable packages.
- CI mechanics, lockfile regeneration, release automation, contributor setup, private playground maintenance, and development-only tests belong here or in contributor documentation, **not in public changelogs**.
- Update a public changelog only when a released package's behavior or public API changes.
- The release-note classification workflow automatically applies `skip-changelog` to maintenance-style PR titles (`chore:`, `ci:`, `docs:`, `test:`, `build:`, `refactor:` and `style:`) or PRs without public package implementation changes. Feature and fix PRs touching published source remain eligible. Reviewers may also apply `skip-changelog` explicitly.
